# v2.3.0 — Portal light and dark appearance

Both customer self-serve and operator cockpit use the same System / Light / Dark appearance control, independently of the operator's brand palette.

## Goal

1. Follow OS appearance by default, with an immediate persistent browser override.
2. Support all six brand palettes in both modes across complete portal surfaces.
3. Preserve email/CLI palettes, hot reload, ownership checks, and cockpit pane scrolling.

## Deliverables

1. `bss-branding` owns dark palettes, paired light palettes, and semantic surfaces. Browser CSS supports explicit root attributes and a CSS media-query fallback.
2. `bss-portal-ui` owns a synchronous head controller and shared accessible selector. Same-origin tabs synchronize; separate origins retain independent preferences. Storage failure allows session-only switching.
3. Both portal layouts include the controller and selector. HTMX/SSE fragments inherit root tokens. Warning/error surfaces, chat and buttons consume paired tokens. QR backgrounds remain white.
4. Branding previews show light and dark portal variants; the email preview remains dark.
5. `BSS_PORTAL_APPEARANCE=system|light|dark` provides a deployment default. Existing deployments can choose dark; saved user preferences win, including an explicit System choice.

## Doctrine and constraints

This extends the historical v1.8 dark-only browser scope; it does not change dark palette values or the email/CLI contract. Palette literals remain in `bss-branding::themes`; the shared CSS phosphor fallback remains pinned. No database migration, business tool, auth change, framework, bundler, or production npm dependency.

## Test strategy

- `cargo fmt --all --check`
- `cargo clippy --workspace --all-targets --all-features -- -D warnings`
- `cargo test --workspace --all-features`
- `bash scripts/rust_doctrine_check.sh`
- `node scripts/test-appearance.cjs`
- `cargo run --quiet -p bss-branding --example browser_palettes > /tmp/theme-palettes.tsv`
- `node scripts/test-appearance-browser.cjs` with an available Playwright installation (`BSS_PLAYWRIGHT_MODULE` supports an absolute path).
- Three consecutive passing hero runs against an isolated disposable stack before tagging. Never run the resetting hero suite on an existing customer dataset.

## Verification checklist

- [x] Shared controls render on public customer pages and cockpit shell.
- [x] Light palette text and button contrast pass the automated 4.5:1 checks.
- [x] OS mode changes, overrides, reload, blocked storage, and tab synchronization pass.
- [x] Browser tests pass all twelve app/palette combinations and inherited fragments.
- [x] Rust workspace, formatting, clippy and doctrine gates pass.
- [ ] PR review/CI and isolated hero release gate pass before merge/tag.

## Out of scope

Cross-origin/account preference synchronization, automatic logo recoloring, and email/CLI appearance changes.

## Session prompt

Read CLAUDE.md, CONTRIBUTING.md and this spec. Implement browser appearance through shared branding/UI seams, preserving dark palettes and domain behavior. Verify every gate and report any unmet release criteria honestly.

## The trap

Inverting backgrounds alone leaves hard-coded alert, badge and chat text unreadable. Appearance must change paired text/surface tokens together. A browser's explicit System choice must override a deployment's dark default.
